\title{Multi-threading vs.\ SIMD Performance Analysis in Smoothed Particle Hydrodynamics on ARM64 Architecture}

\author{Sujal Khatri}
\affil{Department of Computer Science, Fisk University}

\date{March 2026}

\maketitle

\begin{abstract}
Smoothed Particle Hydrodynamics (SPH) is a widely used method for simulating fluids, but its $O(n^2)$ pairwise particle interactions make real-time execution expensive. In this project, we quantify how much a 2D SPH simulation can be accelerated on the Apple M1 processor using two complementary optimization strategies: multi-threading with OpenMP and SIMD vectorization with ARM NEON intrinsics. We implemented four versions of the same simulation---a scalar baseline, an OpenMP-parallelized version, a NEON SIMD version, and a combined version---and benchmarked them on an identical 2,660-particle dam-break scenario. Our results show that OpenMP with 8 threads reaches 58.89~FPS (a 23.0$\times$ speedup over the unoptimized baseline), while single-threaded NEON SIMD reaches 49.69~FPS (19.4$\times$). Combining both approaches reduces total physics computation from 6.169~ms to 3.185~ms per frame, a 5.4$\times$ reduction in the density loop alone. A key finding is that restructuring particle data from Array of Structures (AoS) to Structure of Arrays (SoA) was essential for effective vectorization: a single SIMD-optimized core achieves roughly 85\% of the throughput of 8 threads operating on the unoptimized memory layout, demonstrating that memory layout can be as impactful as the choice of parallelization strategy.
\end{abstract}

\section{Introduction}

Smoothed Particle Hydrodynamics (SPH) is a mesh-free method for simulating fluids in which the fluid is represented as a collection of moving particles rather than values on a spatial grid \cite{muller2003particle}. Each particle carries properties such as position, velocity, and density, and the simulation updates these properties every frame based on interactions with neighboring particles. SPH is particularly effective for free-surface flows, such as splashing water, because the particles naturally track the fluid motion without requiring explicit surface reconstruction.

The central challenge of SPH is performance. Computing each particle's density requires evaluating its distance to every other particle and summing kernel contributions from those within a smoothing radius. In a brute-force implementation, this is an $O(n^2)$ operation: for 2,660 particles, roughly 7 million pair evaluations per frame. The force calculation has the same complexity, and together these two loops dominate the runtime.

Modern processors such as the Apple M1 offer two complementary mechanisms to accelerate this workload. First, the M1 has 8 CPU cores (4 high-performance ``Firestorm'' cores and 4 energy-efficient ``Icestorm'' cores), which can be exploited through thread-level parallelism using OpenMP \cite{openmp2018specification}. Second, each core supports 128-bit ARM NEON SIMD instructions capable of processing four single-precision floats simultaneously \cite{arm2020neon}. These approaches are fundamentally different: multi-threading distributes work across cores (task parallelism), while SIMD increases the amount of work performed per instruction (data parallelism).

In this project, we investigate how each of these approaches performs individually, how they compare, and what gains arise when they are combined. We additionally examine how the choice of memory layout---Array of Structures (AoS) versus Structure of Arrays (SoA)---affects cache efficiency and SIMD effectiveness. To answer these questions, we built four versions of the same SPH simulation and benchmarked them under identical conditions.

\subsection{Research Questions}
This work targets four research questions:
\begin{enumerate}
    \item How much speedup does multi-threading with OpenMP provide for SPH on ARM64?
    \item What performance gains can be achieved through SIMD vectorization with ARM NEON?
    \item How does switching from AoS to SoA memory layout affect cache efficiency?
    \item What are the main architectural bottlenecks for particle simulations on Apple Silicon?
\end{enumerate}

\section{Background}

\subsection{SPH Physics}
Our simulation follows the standard SPH formulation described by M\"uller et al.\ \cite{muller2003particle} and the Eurographics state-of-the-art survey by Koschier et al.\ \cite{koschier2014sph}. Each frame, the simulation performs three sequential steps.

\textbf{Step 1: Density.} For each particle $i$, the local density is computed by summing kernel contributions from all particles $j$ within the smoothing radius $h$:
\begin{equation}
\rho_i = \sum_{j=1}^{N} m_j \, W(|\mathbf{r}_i - \mathbf{r}_j|, h)
\end{equation}
We use the Poly6 kernel for density because it is smooth and depends only on the squared distance $r^2$, which avoids the cost of a square-root operation. Density is then converted to pressure using a simple equation of state:
\begin{equation}
P_i = k(\rho_i - \rho_0)
\end{equation}
where $k = 2000$ is the gas stiffness constant and $\rho_0 = 1.0$ is the rest density.

\textbf{Step 2: Forces.} Each particle accumulates three force contributions---pressure, viscosity, and gravity:
\begin{equation}
\mathbf{F}_i = -\sum_{j} m_j \left( \frac{P_i}{\rho_i^2} + \frac{P_j}{\rho_j^2} \right) \nabla W_{ij} + \mu \sum_{j} m_j \frac{\mathbf{v}_j - \mathbf{v}_i}{\rho_j} \nabla^2 W_{ij} + m_i \mathbf{g}
\end{equation}
The pressure gradient uses the Spiky kernel, which has a sharper peak than Poly6, and viscosity uses the Spiky Laplacian kernel. Both kernels are taken directly from M\"uller et al.\ \cite{muller2003particle}.

\textbf{Step 3: Integration.} Velocities and positions are updated using semi-implicit Euler integration:
\begin{align}
\mathbf{v}_{t+\Delta t} &= \mathbf{v}_t + \frac{\mathbf{F}_t}{\rho_i} \Delta t \\
\mathbf{x}_{t+\Delta t} &= \mathbf{x}_t + \mathbf{v}_{t+\Delta t} \Delta t
\end{align}
Boundary collisions are handled by clamping positions to the domain and reflecting velocities with a damping factor of 0.5.

\subsection{Apple M1 Architecture}
Several properties of the Apple M1 chip \cite{apple2020m1} are directly relevant to our experiments:
\begin{itemize}
    \item \textbf{8 CPU cores:} 4 Firestorm performance cores at 3.2~GHz and 4 Icestorm efficiency cores at 2.0~GHz.
    \item \textbf{128-bit NEON:} Each core supports 4-wide single-precision SIMD operations.
    \item \textbf{Unified memory:} CPU and GPU share the same physical memory, eliminating NUMA penalties for cross-core data access.
    \item \textbf{Cache hierarchy:} 128~KB L1 data cache per core and up to 12~MB shared L2 cache.
\end{itemize}
The unified memory architecture is a double-edged sword: it avoids the coherency overhead of multi-socket systems, but all 8 cores share the same $\sim$68~GB/s memory bandwidth, which can become a bottleneck under parallel memory-intensive workloads.

\section{Methodology}

We implemented four versions of the simulation, each layering an additional optimization on top of the previous stage. All versions use identical physics parameters and the same 2,660-particle dam-break initial condition to ensure a fair comparison.

\subsection{Phase 1: Baseline}
The baseline (\texttt{main\_improved.cpp}) is a single-threaded implementation using an Array of Structures (AoS) layout, in which each particle is a struct containing position, velocity, force, density, and pressure fields. It is compiled with \texttt{-O0} (no compiler optimizations) to establish the true algorithmic cost without contributions from compiler-level optimizations.

This configuration is intentionally slow. Its purpose is to provide a clean worst-case reference point against which subsequent optimizations can be measured.

\subsection{Phase 2: OpenMP Multi-threading}
The OpenMP version (\texttt{main\_omp.cpp}) retains the AoS layout and adds \texttt{\#pragma omp parallel for schedule(static)} to the outer \texttt{i} loop of both the density and force calculations. Because each iteration of the outer loop writes only to \texttt{particles[i]}, no write conflicts arise between threads and no locks or atomic operations are required.

This version is compiled with \texttt{-O2} and linked against Homebrew's \texttt{libomp}. The simulation uses all 8 available hardware threads. We instrumented the density and force loops with \texttt{omp\_get\_wtime()} to obtain per-loop timing measurements.

\subsection{Phase 3: NEON SIMD}
The SIMD version (\texttt{main\_simd.cpp}) introduces two changes: it restructures particle data from AoS to SoA, and it vectorizes the inner \texttt{j} loop using ARM NEON intrinsics.

\textbf{SoA layout.} Instead of a single array of \texttt{Particle} structs, we use separate arrays (\texttt{pos\_x[]}, \texttt{pos\_y[]}, \texttt{vel\_x[]}, etc.). Consequently, when the density loop reads positions, a single 64-byte cache line delivers 16 consecutive \texttt{pos\_x} values, compared to only 2 particles' worth of position data under AoS (each 32-byte struct contains only 8 bytes of position).

\textbf{NEON vectorization.} The inner loop processes 4 particles per iteration using the following intrinsics:
\begin{itemize}
    \item \texttt{vld1q\_f32}: loads 4 floats from a contiguous array
    \item \texttt{vsubq\_f32}, \texttt{vmulq\_f32}, \texttt{vmlaq\_f32}: arithmetic on 4-wide vectors
    \item \texttt{vcltq\_f32} + \texttt{vandq\_u32}: replaces the \texttt{if (r2 < h2)} branch with a branchless mask
    \item \texttt{vrecpeq\_f32} with Newton-Raphson: fast approximate reciprocal (avoids division)
    \item \texttt{vaddvq\_f32}: horizontal sum across all 4 lanes
\end{itemize}
A scalar remainder loop handles the last few particles when $n$ is not a multiple of 4. This version is compiled with \texttt{-O2 -mcpu=apple-m1} and runs on a single thread.

\subsection{Phase 4: Combined (SIMD + OpenMP)}
The combined version (\texttt{main\_combined.cpp}) takes the SoA + NEON code from Phase 3 and wraps the outer \texttt{i} loop with \texttt{\#pragma omp parallel for}. Each thread executes the NEON-vectorized inner loop on its assigned chunk of particles. Because threads write only to their own particle's output fields, no race conditions occur.

Third, the combined version shows only a small FPS gain over OpenMP alone because both are already near the display cap.

The force loop, by contrast, shows essentially no improvement (2.302~ms $\to$ 2.464~ms). The force kernel reads density, pressure, and velocity in addition to position, and requires square-root and reciprocal operations, introducing more data dependencies and reducing opportunities for clean vectorization.

\section{Analysis}

\subsection{RQ1: OpenMP Speedup}
OpenMP achieved a 23$\times$ speedup over the \texttt{-O0} baseline, reaching 58.89~FPS with 8 threads. The density and force loops---the two $O(n^2)$ bottlenecks---are embarrassingly parallel at the outer loop level because each particle's computation is independent of the others.

It is important to note that this 23$\times$ figure includes both the effect of multi-threading \emph{and} the switch from \texttt{-O0} to \texttt{-O2}. The \texttt{-O2} flag alone likely accounts for a substantial portion of the speedup through loop unrolling, improved register allocation, and instruction scheduling. Isolating the pure threading contribution would require running the single-threaded AoS version at \texttt{-O2}, which we identify as future work.

The M1's unified memory architecture contributes to smooth thread scaling, as all cores share the same physical memory without NUMA penalties. However, because the Icestorm cores run at 2.0~GHz while the Firestorm cores run at 3.2~GHz, 8-thread scaling is sub-linear (i.e., less than 8$\times$ over a single-threaded run).

\subsection{RQ2: SIMD Performance}
Single-threaded NEON SIMD reached 49.69~FPS, approximately 85\% of the 8-thread OpenMP result. This is a striking finding: a single carefully optimized core nearly matches 8 cores running unoptimized code.

The theoretical maximum SIMD speedup for 128-bit vectors on 32-bit floats is 4$\times$, but the observed gains arise from several compounding factors:
\begin{itemize}
    \item Processing 4 particles per inner loop iteration reduces loop overhead.
    \item Branchless masking (\texttt{vcltq\_f32} combined with \texttt{vandq\_u32}) eliminates branch mispredictions that would otherwise stall the pipeline.
    \item The SoA layout enables full cache-line utilization for vector loads.
    \item The \texttt{-O2} compiler flag further optimizes the surrounding scalar code.
\end{itemize}

\subsection{RQ3: AoS vs.\ SoA and Cache Efficiency}
The memory layout change is arguably the single most impactful optimization in this work. Under AoS, each \texttt{Particle} struct is 32~bytes, so a 64-byte cache line holds only 2 particles. Yet the density kernel reads only position data (8~bytes per particle), meaning 75\% of each cache line load is wasted on velocity, force, and other fields that are not accessed during density computation.

Under SoA, the \texttt{pos\_x} array is contiguous, so a single cache line holds 16 consecutive x-positions. The density kernel reads \texttt{pos\_x[j..j+3]} and \texttt{pos\_y[j..j+3]}---two 16-byte loads that fully utilize the data brought into cache.

The per-loop timing data supports this analysis. For the density loop, which reads only positions, the combined SoA+NEON version is 5.4$\times$ faster than the AoS OpenMP version (0.722~ms vs.\ 3.867~ms). The force loop, which accesses more fields with less regular access patterns, shows essentially no improvement.

The broader takeaway is that \textbf{how data is laid out in memory matters as much as, if not more than, how the computation is parallelized.}

\subsection{RQ4: Architectural Bottlenecks}
The dominant bottleneck shifts as successive optimizations are applied:
\begin{enumerate}
    \item \textbf{Baseline:} Purely compute-bound. With \texttt{-O0} and scalar loops, the CPU spends almost all its time on arithmetic for roughly 7 million pair interactions per frame.
    \item \textbf{OpenMP:} Still largely compute-bound, but the density loop (3.87~ms) is 1.7$\times$ slower than the force loop (2.30~ms), indicating that memory access patterns are beginning to matter---the density kernel touches more data per unit of computation.
    \item \textbf{Combined:} With total physics time reduced to 3.185~ms per frame (a theoretical ceiling of $\sim$313~FPS without the display cap), the simulation is approaching the memory bandwidth limit, as 8 cores running SIMD all compete for the same $\sim$68~GB/s memory bus.
    \item \textbf{Algorithmic ceiling:} Regardless of optimization, the $O(n^2)$ algorithm itself imposes a fundamental ceiling. At 2,660 particles, 60~FPS is achievable, but scaling to 10,000 or more particles would require a fundamentally different approach, such as a spatial hash grid, to reduce the complexity to $O(n \cdot k)$, where $k$ is the average number of neighbors.
\end{enumerate}

\section{3D Extension}
As a supplementary experiment, we extended the simulation to 3D with an interactive rotatable cube container. The 3D version reuses the SoA + NEON optimizations for physics.

An interesting finding was that \emph{rendering}, not physics, became the primary bottleneck in 3D. Using Raylib's \texttt{DrawSphere} function (which draws a full 3D mesh per particle) yielded only 18.26~FPS with 1,331 particles. Switching to a lightweight GL point rendering approach using \texttt{rlBegin(RL\_LINES)} raised performance to 58.27~FPS with 1,575 particles---a 3.2$\times$ improvement from the rendering change alone.

\section{Limitations}

Several aspects of this study could be strengthened in a more thorough investigation:

\begin{itemize}
    \item \textbf{Compiler flag confound.} The baseline uses \texttt{-O0} while the optimized versions use \texttt{-O2}, so the reported speedup figures conflate compiler optimization gains with threading and SIMD gains. Running the baseline at \texttt{-O2} would yield a cleaner comparison.
    \item \textbf{No hardware profiling.} We did not collect cache miss rates, branch misprediction counts, or memory bandwidth measurements from hardware performance counters. Tools such as Apple Instruments or Linux \texttt{perf} would allow our cache efficiency claims to be validated with direct measurements.
    \item \textbf{Single particle count.} All optimized benchmarks use $n = 2660$. Additional runs at larger counts (e.g., 5,000; 10,000; 50,000) would reveal where each optimization breaks down.
    \item \textbf{No thread scaling curve.} We only tested with 8 threads. A sweep across 1, 2, 4, and 8 threads would reveal whether scaling is linear or plateaus.
\end{itemize}

\section{Future Work}

The most impactful next step is implementing a \textbf{spatial hash grid} to reduce algorithmic complexity from $O(n^2)$ to $O(n \cdot k)$, where $k$ is the average number of neighbors per particle. This would likely yield larger speedups than all of our current optimizations combined, particularly at higher particle counts.

Additional directions include:
\begin{itemize}
    \item Collecting hardware performance counters to validate the cache efficiency analysis quantitatively.
    \item Measuring scaling behavior at 10,000 or more particles.
    \item Exploring GPU acceleration via Apple's Metal API to move the computation entirely off the CPU.
    \item Performing a direct comparison against compiler auto-vectorization to isolate the benefits of manual NEON tuning.
\end{itemize}

\section{Conclusion}

In this project, we measured the impact of multi-threading and SIMD vectorization on a 2D SPH fluid simulation running on the Apple M1. Our main findings are as follows:

\begin{enumerate}
    \item OpenMP multi-threading with 8 threads reaches 58.89~FPS (23$\times$ over the unoptimized baseline), reducing the per-frame physics computation to 6.169~ms.
    \item Single-threaded NEON SIMD reaches 49.69~FPS (19.4$\times$), achieving roughly 85\% of the 8-thread OpenMP result on a single core.
    \item Combining both approaches reduces total physics time to 3.185~ms per frame, with the density loop alone dropping 5.4$\times$ due to SoA restructuring.
    \item Memory layout (AoS vs.\ SoA) has at least as much impact as the choice of parallelization strategy. The SoA transformation was essential for making SIMD effective and significantly improved cache utilization.
\end{enumerate}

The overarching lesson is that optimizing \emph{how} data is accessed matters as much as optimizing \emph{how much} computation is performed in parallel. A single well-optimized core with cache-friendly data layout can approach the performance of many cores operating on poorly structured data.
